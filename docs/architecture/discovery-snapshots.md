# 변경 기반 행사 스냅샷 / 앱 로컬 조회

작성·갱신: 2026-09-13. D1 0032 적용, Worker 6890b1c5-e3d9-4a62-92e1-565e009ae939 배포 완료. 최초 발행 진행 중. iOS 검증·TestFlight는 아직 완료하지 않았다.

## 데이터 흐름

기존 수집·보강·관리 → D1 변경 트리거 → 고정 묶음 발행 → R2 공개 manifest → 앱 디스크/공간 인덱스.

- 최초에는 discovery/local 각각 64개 묶음을 모두 처리한다. 이후에는 변경된 묶음만 인덱스로 읽는다.
- 수집기의 구간과 배포 묶음은 다르다. ID의 고정 해시로 배포 묶음을 정하므로 다른 구간의 추가/삭제가 전체 파일 경계를 이동시키지 않는다.
- 공개 내용 변경과 변경 기록은 같은 DB 트랜잭션으로 저장된다. 단순 last_seen_at/data_updated_at 갱신은 제외한다. 공개 DTO에 영향 없는 raw_payload 변경은 해시 비교로 최종 재발행을 생략한다.
- 수정/삭제/좌표 보강/승인 취소/비공개 전환을 추적한다. 수집 함수의 정상 반환만을 성공으로 간주하지 않는다. 실제 커밋된 행만 기록한다.
- 원본에 없는 행사를 새로 찾아주는 기능은 아니다. RoboCup 같은 원본 수집 범위 문제는 별도로 해결해야 한다.

## 서버 계약과 일관성

- GET /api/discovery-snapshot/manifest.json: schemaVersion=1, version(UUID), generatedAt, revision, parts[{sha256,bytes,count}], count.
- GET /api/discovery-snapshot/status.json: 발행 검사 시각 checkedAt, healthy, pending/pendingSince 또는 error/retryAt. 데이터 변경 시각과 발행기 확인 시각을 분리한다. 원본 공급자 전체의 건강도를 보증하는 지표는 아니다.
- GET /api/discovery-snapshot/parts/<sha256>.json: 공개 DTO만. raw payload·관리 메모 제외.
- R2 직접 키는 discovery/v1/ 하위다. catalog.json, incremental-build.json, queue-budget.json 등 내부 키는 HTTP 공개 경로에서 404다.
- manifest/status 캐시 30초, 해시 파일 1년 immutable, ETag 지원. D1 장애 시 SQL API로 우회하지 않는다.
- 기존 일일 10:07/10:17/10:37 일정은 제거했다. 매분 스케줄러가 작은 미처리 변경 인덱스를 확인한다. 변화가 없으면 이벤트 테이블과 Queue를 사용하지 않는다.
- 일반 행사는 최초 미처리 변경 이후 2분 합치기, 지역/사장님 행사는 다음 검사에서 우선 처리한다. 밀린 작업과 자원 예산에 따라 실제 지연은 늘어날 수 있다.
- Queue 한 회차는 해당 bucket의 id > cursor ORDER BY id LIMIT 128만 읽는다. 128은 작업 분할 크기이지 총 핀 제한이 아니다. 필터 결과가 비어도 원본 EOF까지 처리한다.
- 모든 128개 묶음이 준비되기 전에는 최초 공개 manifest를 만들지 않는다. 이후에는 해당 묶음만 교체한 새 목록을 조건부 쓰기로 발행한다.
- R2 체크포인트/CAS와 단조 증가 revision이 중복 Queue·순서 역전·재시도를 방어한다. DB는 발행 시작 당시 revision까지만 확인 처리한다. 동시에 생긴 새 변경은 미처리로 남는다.
- 여러 페이지 조회가 DB 전체의 단일 시점 트랜잭션인 것은 아니다. 조회 중 변경은 다음 발행으로 수렴한다.
- 명시적인 DB 삭제로 묶음이 비면 빈 묶음 교체가 허용된다. 초기 앱 릴리스 검사는 전체 0건을 차단한다.
- 일반 오류는 60초 후, D1 일일 한도 오류는 다음 UTC 00:01 이후 재개한다. 불완전한 파일은 공개하지 않고 이전 manifest를 유지한다.

## 실시간 주차

- 기존 분 단위 shard 수집 주기를 유지한다. 수집된 공개 DTO를 parking/v1/shard-N.json으로 추가 발행하며, 이를 위해 D1을 다시 내보내지 않는다.
- /parking/realtime은 R2/30초 공유 엣지 캐시만 읽고 요청 지역을 필터링한다. 기존 1,000개 결과 제한을 사용하지 않는다. /parking/realtime/clusters 및 정적 주차 API는 아직 별도 D1 경로다.
- 공급자가 오류를 내부에서 삼켜도 건강 상태/성공 시각을 검사해 실패한 shard를 덮어쓰지 않는다. 빈 수집은 이전 파일을 유지한다.
- 원본 시각이 10분 이상 오래되면 핀 위치는 유지하되 잔여면수는 unknown으로 바꾼다. 초기 생성되지 않은 shard 수는 X-Realtime-Missing-Shards 헤더로 구분한다. 모든 shard가 없으면 503이다.
- 앱은 지도 탭이 활성이고 주차 레이어가 켜져 있을 때 현재 영역을 45초 간격으로 확인한다. 지도 이동은 debounce, 취소 및 요청 순서 가드를 적용한다. 실패 후 60초 재시도 대기, 기존 핀 유지.

## iOS

- 첫 사용에는 행사 파일 전체를 최대 4개 병렬 다운로드한다. 이후 지도 이동/날짜/지역 검색은 디스크 데이터의 로컬 공간 인덱스로 수행한다.
- 활성 지도/이벤트/달력 화면에서 60초 간격으로 버전을 확인한다. 공통 actor가 요청을 합치고 실패 시 5분 대기한다. iOS 백그라운드에서 고정 주기를 보장하지 않는다.
- 변경된 해시 파일만 내려받고 무결성·크기·건수·스키마·좌표를 검사한 뒤 로컬 manifest를 atomic 교체한다. 통신 실패/앱 종료 때 이전 완성본을 보존한다.
- 새 버전 알림으로 지도·목록·달력·위젯 요약을 갱신한다. 날짜/노출 만료는 기기에서 다시 계산한다.
- 첫 설치 오프라인은 저장본이 없으므로 핀을 표시할 수 없다. 지도 바탕 타일/이미지 오프라인도 별도다. 번들 고정 데이터는 넣지 않았다.

## 예산과 제한

- 안전 크기: 파일 8 MiB, manifest 4 MiB, 전체 128 MiB. 초과 시 일부를 잘라내지 않고 발행을 중단한다. 실기기 메모리 보장값은 아니다.
- 발행 Queue 신규 메시지 최대 700/UTC일(통상 2,100 operations). 기존 최악 추산 7,446 ops와 합계 9,546이며 재시도/다른 생산자는 별도 관찰이 필요하다. 전체 계정 사용량을 강제 제한하는 장치는 아니다.
- 발행 스캔의 정상 페이지 처리 상한은 700 × 128 = 89,600행/일보다 작다. 중복 처리, 인덱스 읽기, 트리거·수집 작업은 별도다. 실제 D1 rows_read와 쓰기량을 측정해야 한다.
- 예산 소진 시 미처리 기록/체크포인트를 유지하고 다음 날 재개한다. 핀을 삭제하거나 일부만 배포하지 않는다.
- 사용자 요청은 Worker 무료 요청 한도와 R2 읽기량을 여전히 사용한다. 사용량이 커지면 별도 R2 커스텀 도메인/CDN이 필요하다. 이번 작업에서 유료 플랜·추가 권한은 변경하지 않았다.
- 서버 해시 파일은 아직 자동 GC하지 않는다. 최신/생성 중 참조 및 다운로드 유예기간을 보존하는 GC가 필요하다. 앱은 미사용 파일을 정리한다.
- 다른 공급자 ID 중복, 정적 주차, 검색/신고/관리/알림 및 구버전 앱 D1 사용량은 남는다.

## 배포·검증

1. 기존 R2 바인딩 확인 → D1 0032 적용 → Worker 배포.
2. Worker 체크포인트 전진과 실제 rowsRead 확인. CLI 한 행 조회만으로 한도 해제를 판단하지 않는다.
3. node worker-backend/scripts/verify-discovery-snapshot.mjs: 전체 manifest/파일 해시·바이트·건수·좌표 확인. 데이터가 오래되어도 정상 무변경일 수 있으므로 48시간 생성일 제한 대신 발행기 최근 15분 검사와 10분 미만 backlog를 검사한다.
4. Codemagic 시뮬레이터 검증 후 TestFlight. 완성 데이터 검증 전 TestFlight 금지. App Store 공개는 별도 승인 사항.
5. 최초 다운로드 크기/시간/메모리, 종료 후 재개, 오프라인, 변경/삭제/취소, 지도 이동, 주차 갱신을 실기기로 확인한다.
