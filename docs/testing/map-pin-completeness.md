# 지도 행사 핀 누락 회귀 검증

2026-09-12 로컬 구현. Worker 배포 및 iOS 빌드/실기 검증은 아직 하지 않았다.

## 변경

- 화면 근처 행사 중 가까운 600개만 남기던 제한을 제거했다. 화면 밖 제외, 클러스터링, 프레임별 분할 렌더링은 유지한다.
- 행사/공연 조회의 전체 5,000개 제한을 제거했다. 새 앱은 `/api/festivals`, `/api/performances`, `/api/local-events`에 `paged=true`를 보내고 `nextCursor`가 null일 때까지 읽는다.
- 페이지는 원본 행 id 기준 keyset이며 SQL 256행은 전송 단위이지 총 결과 상한이 아니다. 날짜/거리 필터로 응답 배열이 비어도 커서가 있으면 계속 읽어야 한다. 페이지 도중 실패나 반복 커서는 완료가 아니라 오류다.
- `paged` 없는 구버전 호출은 기존 응답 형태를 유지한다. 지역 행사 구버전 offset 조회도 스캔 상한 때문에 조기 종료하지 않는다.
- 응답은 요청 세대 번호와 취소 여부를 확인한 뒤 반영한다. 조회 완료 범위와 필터도 같은 시점에 기록한다. 실패한 범위는 재조회 가능 상태로 남긴다.
- 조회 반경은 화면 반경의 1.6배(최소 20km)로 표시 여유 1.35배와 이동 임계값 0.15배를 덮는다. 카메라 반경은 네 모서리 중 최대 거리로 계산한다.
- 실제 SDK에 추가된 핀만 렌더 완료로 기록한다. 미추가 핀은 1초 간격으로 재시도한다.
- 사용자 지도 이동 후 초기 행사/늦은 위치 응답에 의한 자동 재중앙 이동을 막는다. 명시적인 내 위치 버튼은 유지한다.

## 자동 검증

- Worker: 37개 파일, 318개 테스트 통과. 5,501개 행사, 빈 중간 페이지 뒤 공연, 원 밖 후보 256개 뒤 지역 행사, offset 호환성 포함.
- backend: 23개 파일, 73개 테스트 통과.
- Worker `tsc --noEmit` 통과.
- iOS에 `MapViewportSelectionTests`, `MapDiscoveryLoadingTests`, API 페이지네이션 회귀 테스트 추가. Windows 환경이므로 Xcode 테스트는 미실행.
- 테스트 설정은 남아 있는 로컬 `.js` 산출물보다 `.ts` 원본을 우선한다. 통계 테스트의 Windows/한글 경로 처리도 수정했다.

## 배포 및 실기 확인

1. Worker를 먼저 배포하고 세 endpoint의 `paged=true` 응답에 `nextCursor`가 있는지 확인한다. 페이지 사이에는 좌표/반경/기간 조건을 바꾸지 않는다.
2. iOS XcodeGen 프로젝트 재생성 후 XCTest를 실행하고 새 앱을 빌드한다. D1 마이그레이션은 필요 없다.
3. 밀집 지역에서 600개 이상이 클러스터 개수에 포함되는지, 확대하면 해당 개별 핀/동일 장소 묶음으로 접근 가능한지 확인한다.
4. 서울 → 송도 → 서울로 빠르게 이동하고 응답 순서를 지연시킨다. 마지막 화면의 결과를 이전 요청이 덮어쓰지 않아야 한다.
5. 같은 화면에서 로컬 행사/공연 토글을 바꿔도 사용자가 선택한 날짜·지역 필터가 유지되어야 한다.
6. 두 번째 페이지에 네트워크 오류를 주고 다시 지도를 움직인다. 일부 결과를 전체 조회 완료로 기억하지 않고 재시도해야 한다.
7. 권한 없이 실행 직후 지도를 움직이거나, 위치 응답을 지연시킨다. 자동으로 최초 지역으로 돌아가지 않아야 한다.
8. 회전/기울기 및 확대/축소 시 화면 모서리 핀, SDK 부분 추가 실패 재시도, 메모리/프레임 시간을 실기에서 확인한다.

## 범위와 주의

- 기간/지역/분류 필터, 만료/미승인 행사 제외, 부정확한 지역 대표 좌표 제외는 의도된 정책으로 유지했다. 원천에 수집되지 않은 행사가 새로 생기는 변경은 아니다.
- 클러스터는 핀 삭제가 아니라 묶음이다. 축소 화면의 아이콘 수와 실제 행사 수는 다를 수 있다.
- 페이지별 중복 정리와 앱의 id 중복 제거를 적용한다. 서로 다른 출처의 의미상 동일 행사가 다른 페이지에 걸친 경우, 전역 의미 중복 병합은 별도 개선 대상이다.
- 구버전 비페이지 조회는 전체 결과를 모으므로 대규모 범위에서는 응답 비용이 크다. 새 앱의 페이지 조회를 우선 배포한다.
